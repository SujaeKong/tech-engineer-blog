## 1. 뉴스 요약

아이뉴스24(11-23)는 **사이버 침해사고가 31% 급증했고 AI를 이용한 대규모 공격이 가능해졌다**고 단독 보도했다. 같은 날 조선일보(11-23)는 **사이버 보안기업들이 '해킹 차단 성벽'을 제품 설계 단계부터 함께 짓는 쪽으로 AI 기술 확보에 나섰다**고 전했다. 완성된 제품에 보안 장비를 덧대는 방식으로는 AI로 빨라진 공격 속도를 따라가기 어렵다는 인식이다. 집계 기준과 기업별 사례는 제목 이상으로 확인되지 않으므로, 아래에서는 **보안을 설계 단계부터 내재화하는 시큐어 바이 디자인**을 답안 재료로 정리한다.

## 2. 핵심 개념

### 정의
**시큐어 바이 디자인**(Secure by Design)은 제품·시스템을 만드는 **요구사항·설계 단계부터 보안을 핵심 품질 요구로 반영해, 알려진 취약점 유형이 구조적으로 생기지 않도록** 만드는 원칙이다. **시큐어 바이 디폴트**(Secure by Default)는 제품을 **별도 설정 없이 설치한 상태 그대로 안전하게** 동작하도록 하는 원칙으로, 다중 인증 기본 활성화·기본 비밀번호 제거 등이 대표 예다. 두 원칙 모두 보안 책임을 사용자에게 떠넘기지 말고 **제조사가 지라**는 방향을 담고 있다.

### 사후 보완형 보안 vs 시큐어 바이 디자인

| 구분 | 사후 보완형(Bolt-on) | 시큐어 바이 디자인 |
|---|---|---|
| 보안 반영 시점 | 개발 완료 후·배포 후 | 요구사항·설계부터 전 단계 |
| 주 수단 | 방화벽·패치·보안 장비 추가 | 위협 모델링·안전한 아키텍처·안전한 언어·기본값 |
| 책임 주체 | 사용자·운영자가 설정·보완 | 제조사가 기본 안전 보장 |
| 취약점 대응 | 개별 취약점 발견 후 패치 | 취약점 유형 자체를 제거 |
| 비용 | 후반으로 갈수록 수정 비용 급증 | 초기 투자, 전체 비용 감소 |
| 고객 경험 | 보안 설정 부담 큼 | 설치 즉시 안전 |
| 투명성 | 취약점 공개 소극적 | 취약점·보안 지표 적극 공개 |

### 3대 원칙
미국 CISA가 여러 나라 보안기관과 함께 제시한 시큐어 바이 디자인 원칙은 세 가지로 정리된다.
1. **고객 보안 결과에 대한 책임**: 사용자가 보안 설정을 잘못해도 안전하도록 제조사가 책임진다.
2. **철저한 투명성과 책임성**: 취약점 정보(CVE)를 정확히 공개하고, 보안 개선 지표를 밝힌다.
3. **경영진 주도**: 보안을 기술 부서의 일이 아니라 경영 목표로 삼고 조직 구조와 보상에 반영한다.

### 시큐어 바이 디폴트의 예
- 다중 인증(MFA)을 기본 활성화하고, 관리자 계정은 필수 적용
- 공통 기본 비밀번호 제거, 최초 설치 시 고유 비밀번호 강제
- 보안 로그를 추가 비용 없이 기본 제공
- 불필요한 서비스·포트는 기본 비활성화
- 안전하지 않은 레거시 프로토콜은 기본 차단, 필요할 때만 명시적으로 켬

### 구성도 ① — 보안 개발 생명주기(SSDLC)

```
 [요구사항]  보안 요구사항 정의 · 법·규제 요구 · 데이터 분류
     │
     ▼
 [설계]      위협 모델링(STRIDE) · 보안 아키텍처 검토 · 안전한 기본값 설계
     │
     ▼
 [구현]      시큐어 코딩 · 메모리 안전 언어 · 정적 분석(SAST) · 의존성 점검(SCA)
     │
     ▼
 [검증]      동적 분석(DAST) · 침투 테스트 · 퍼징 · SBOM 생성
     │
     ▼
 [배포]      서명된 배포 · 안전한 설정 기본값 · 공급망 무결성
     │
     ▼
 [운영]      취약점 접수·공개 정책 · 패치 · 보안 로그 · 사고 대응
     │
     └──▶ 발견된 취약점 유형을 [요구사항·설계]로 환류 → 유형 단위 제거
```

### 위협 모델링 — STRIDE

| 위협 | 의미 | 침해되는 보안 속성 | 대표 대책 |
|---|---|---|---|
| Spoofing(위장) | 다른 사용자·시스템으로 가장 | 인증 | 강한 인증, MFA |
| Tampering(변조) | 데이터·코드 무단 변경 | 무결성 | 전자서명, 해시, 접근 통제 |
| Repudiation(부인) | 수행한 행위를 부인 | 부인 방지 | 감사 로그, 서명 |
| Information Disclosure(정보 노출) | 권한 없는 정보 열람 | 기밀성 | 암호화, 최소 권한 |
| Denial of Service(서비스 거부) | 서비스 사용 불가 유발 | 가용성 | 속도 제한, 이중화 |
| Elevation of Privilege(권한 상승) | 낮은 권한으로 높은 권한 획득 | 인가 | 권한 분리, 입력 검증 |

설계 단계에서 데이터 흐름도를 그리고, 각 구성요소와 경계마다 STRIDE를 대입해 위협을 찾는다. 찾은 위협은 위험도 순으로 대책을 설계에 반영한다.

### 취약점 유형 제거 접근
개별 버그를 하나씩 고치는 대신, **같은 종류의 취약점이 다시 생기지 않는 구조**를 만든다.
- **메모리 안전성**: 버퍼 오버플로·해제 후 사용 같은 메모리 취약점은 메모리 안전 언어로 전환해 유형 자체를 줄인다.
- **SQL 인젝션**: 문자열 조립 대신 매개변수화된 질의를 프레임워크 차원에서 강제한다.
- **XSS**: 출력 시 자동 이스케이프가 기본인 템플릿 엔진을 쓴다.
- **인증 우회**: 인증·인가 로직을 공통 모듈로 모아 개별 구현을 금지한다.

### 구성도 ② — 보안 내재화 거버넌스

```
 [경영진]  보안을 경영 목표로 설정 · 보안 지표 공개 · 예산·인력 배정
     │
     ▼
 [보안 챔피언]  개발 조직 안의 보안 담당자 — 위협 모델링·리뷰 주도
     │
     ▼
 [개발 파이프라인]  SAST·SCA·DAST·비밀값 탐지 자동 게이트
     │
     ▼
 [제품 출시 기준]  위협 모델 완료 · 고위험 취약점 0건 · SBOM 제출
     │
     ▼
 [사후]  취약점 공개 정책 · 버그 바운티 · 원인 분석 → 기준 갱신
```

### 관련 표준·법령
- **NIST SP 800-218 SSDF**: 보안 소프트웨어 개발 프레임워크(조직 준비·SW 보호·안전한 SW 생산·취약점 대응)
- **EU 사이버 복원력법**(CRA): 디지털 요소가 있는 제품에 설계 단계 보안·취약점 처리·보안 업데이트 의무 부과
- **OWASP SAMM**: 소프트웨어 보안 성숙도 모델
- **ISO/IEC 27034**: 애플리케이션 보안
- **국내 SW 개발보안 제도**: 행정·공공기관 정보시스템 구축 시 보안약점 진단·제거 의무

## 3. 기술사 출제 포인트

- 시큐어 바이 디자인과 시큐어 바이 디폴트의 정의와 차이
- 사후 보완형 보안과 설계 내재형 보안 비교
- CISA 3대 원칙(고객 보안 결과 책임·투명성·경영진 주도)
- 시큐어 바이 디폴트 예(MFA 기본·기본 비밀번호 제거·로그 기본 제공)
- 보안 개발 생명주기(SSDLC) 단계별 활동
- STRIDE 위협 모델링과 보안 속성 매핑
- 취약점 유형 제거(메모리 안전 언어·매개변수화 질의·자동 이스케이프)
- 보안 챔피언과 파이프라인 자동 게이트
- NIST SSDF·EU CRA·국내 SW 개발보안 제도

## 4. 연결 기출 토픽과 예상 변형

- **SW 공급망**: 140회 2교시에 **오픈소스 라이선스와 SW 공급망**이 출제됐다. SBOM·의존성 점검·서명된 배포는 시큐어 바이 디자인의 공급망 단계에 해당한다.
- **CTEM**: 139회 1교시에 **CTEM**이 출제됐다. 운영 중 노출을 줄이는 CTEM과, 처음부터 노출을 만들지 않는 시큐어 바이 디자인을 짝지어 쓰면 예방–운영 전 주기 답안이 된다.
- **기술부채**: 139회 3교시에 **기술부채**가 출제됐다. 보안을 미룬 설계는 나중에 비싼 대가를 치르는 보안 부채로 볼 수 있다.
- **정보보호 컴플라이언스**: 140회 4교시에 **정보보호 컴플라이언스**가 출제됐다. EU CRA처럼 설계 보안을 법적 의무로 만드는 흐름과 연결된다.
- **예상 변형**
  - 1교시: "시큐어 바이 디자인(Secure by Design)과 시큐어 바이 디폴트(Secure by Default)를 비교하시오"
  - 1교시: "STRIDE 위협 모델링을 설명하시오"
  - 논술: "AI 기반 공격 증가에 대응한 소프트웨어 보안 내재화 전략을 생명주기 관점에서 제시하시오"

## 5. 답안 구성 예시

**단답형**(1교시, 1페이지)
- 정의: 요구사항·설계 단계부터 보안을 핵심 품질로 반영해 취약점 유형이 구조적으로 생기지 않도록 하는 원칙
- 특징 3개: ① 제조사가 고객 보안 결과에 책임 ② 취약점 유형 단위 제거 ③ 안전한 기본값(Secure by Default) 동반
- 구성도 키워드: 요구사항 → 설계(STRIDE) → 구현(시큐어 코딩·SAST) → 검증(DAST·퍼징) → 배포(서명·SBOM) → 운영(취약점 공개·패치) → 환류

**논술형(2~4교시) 목차**
1. 개요: 침해사고 급증·AI 공격 고도화와 사후 보완형 보안의 한계
2. 구성/비교: 사후 보완형 vs 설계 내재형 비교표, SSDLC 구성도, STRIDE 표, 거버넌스 구성도
3. 적용방안: 위협 모델링 의무화, 메모리 안전 언어 전환 로드맵, 파이프라인 자동 게이트, 안전한 기본값 체크리스트, 보안 챔피언 제도, 취약점 공개 정책
4. 고려사항: 초기 개발 비용·일정 부담, 레거시 시스템 전환, 개발자 역량, 규제 대응(CRA 등)
5. 기술사 제언: 보안 성과를 패치 건수가 아니라 **제거한 취약점 유형 수와 기본값 안전성**으로 측정하고, 출시 기준에 위협 모델 완료와 SBOM 제출을 넣어 설계 보안을 제도화할 것
