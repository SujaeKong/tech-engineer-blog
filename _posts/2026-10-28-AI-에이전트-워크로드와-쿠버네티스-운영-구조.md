## 1. 뉴스 요약

애플경제(10-26)는 "**AI 에이전트와 쿠버네티스, '궁합' 맞으려면?**"이라는 제목으로, AI 에이전트를 컨테이너 오케스트레이션 환경에서 운영할 때의 과제를 다뤘다. 쿠버네티스는 짧은 요청을 처리하고 상태를 갖지 않는 웹 서비스를 전제로 발전해 왔는데, 에이전트는 **오래 실행되고, 대화 상태를 유지하며, 도구를 호출하고 코드를 실행**한다는 점에서 성격이 다르다. 기사의 구체 내용은 제목 이상으로 확인되지 않으므로, 아래에서는 에이전트 워크로드의 특성과 쿠버네티스 운영 구조를 답안 재료로 정리한다.

## 2. 핵심 개념

### 정의
**AI 에이전트 워크로드**는 LLM이 목표를 받아 **계획 → 도구 호출 → 결과 확인 → 다음 행동**을 반복하며 작업을 수행하는 실행 단위다. 이를 쿠버네티스에서 운영하려면 무상태 웹 서비스 기준으로 설계된 기본 구성 위에 **세션 상태 관리, 신뢰할 수 없는 코드의 격리 실행, 작업량 기반 확장, 단계별 추적**을 추가해야 한다.

### 웹 서비스 vs AI 에이전트 워크로드

| 구분 | 일반 웹 서비스 | AI 에이전트 |
|---|---|---|
| 실행 시간 | 밀리초~초 | 수 분~수 시간 |
| 상태 | 무상태(Stateless) | 대화·작업 상태 유지(Stateful) |
| 부하 패턴 | 요청 수에 비례 | 작업 단위로 들쭉날쭉(Bursty) |
| 실행 코드 | 개발자가 작성한 검증된 코드 | LLM이 생성한 코드·명령 실행 |
| 외부 호출 | 정해진 API | 다양한 도구·웹·사내 시스템 |
| 실패 처리 | 재시도로 충분 | 중간 단계부터 재개 필요 |
| 비용 구조 | CPU·메모리 | LLM 토큰·GPU 추론 비용 |
| 관측 단위 | 요청·응답 | 작업 전체의 단계별 궤적 |

### 구성도 — 쿠버네티스 기반 에이전트 운영 구조

```
 사용자 / 이벤트 ──▶ [API 게이트웨이] ──▶ [작업 큐]
                                           │ 큐 길이 기반 확장(이벤트 오토스케일)
                                           ▼
 ┌──────────────── 쿠버네티스 클러스터 ────────────────────────┐
 │ [에이전트 실행 Pod]  계획·도구 호출 루프                    │
 │      │  세션 상태 ──▶ [상태 저장소] (DB·캐시, 체크포인트)   │
 │      │                                                      │
 │      ├─▶ [샌드박스] 생성 코드 실행 (마이크로VM·강화 런타임)  │
 │      │      └ 네트워크 차단·자원 제한·실행 후 폐기          │
 │      ├─▶ [도구 게이트웨이] 사내 API·웹 접근 (허용 목록·감사) │
 │      └─▶ [LLM 추론 서비스] GPU 노드풀 (모델 서빙)            │
 │                                                              │
 │ [관측성] 단계별 트레이스 · 토큰 사용량 · 도구 호출 로그       │
 └──────────────────────────────────────────────────────────────┘
```

### 핵심 설계 요소
- **상태 외부화와 체크포인트**: Pod는 언제든 재시작될 수 있다. 세션 상태와 작업 진행 단계를 외부 저장소에 저장해, Pod가 교체돼도 **중단된 단계부터 이어서** 실행한다.
- **코드 실행 격리**: LLM이 만든 코드는 신뢰할 수 없다. 일반 컨테이너는 호스트 커널을 공유하므로, 마이크로VM이나 강화된 컨테이너 런타임으로 **커널 수준까지 격리**하고 실행 후 폐기한다.
- **이벤트 기반 확장**: CPU 사용률 기반 수평 확장(HPA)은 에이전트에 잘 맞지 않는다. 대기 중인 작업 수(큐 길이)를 기준으로 확장·축소한다.
- **도구 접근 통제**: 에이전트가 호출할 수 있는 도구와 목적지를 허용 목록으로 제한하고, 외부로 나가는 트래픽(egress)을 게이트웨이로 모은다.
- **자원 분리**: 에이전트 실행(CPU)과 LLM 추론(GPU)을 다른 노드풀로 나눠, 비싼 GPU가 대기 시간에 묶이지 않게 한다.

### 컨테이너 격리 수준 비교

| 방식 | 격리 경계 | 기동 속도 | 적합 용도 |
|---|---|---|---|
| 일반 컨테이너 | 네임스페이스·cgroup(커널 공유) | 매우 빠름 | 검증된 에이전트 로직 |
| 강화 런타임(사용자 공간 커널) | 시스템 호출 가로채기 | 빠름 | 중간 위험 코드 |
| 마이크로VM | 경량 가상머신(별도 커널) | 빠름(수백 ms 수준) | LLM 생성 코드 실행 |
| 전용 VM | 완전 가상화 | 느림 | 고위험·장기 실행 작업 |

### 관련 기준
- **쿠버네티스 Pod 보안 표준**(Privileged·Baseline·Restricted): 에이전트 실행 Pod는 Restricted 수준 권장
- **런타임 클래스**(RuntimeClass): Pod별로 다른 격리 런타임을 지정하는 쿠버네티스 기능
- **OpenTelemetry**: 분산 트레이싱 표준 — 에이전트의 단계별 궤적 추적에 활용

## 3. 기술사 출제 포인트

- AI 에이전트 워크로드의 특성(장기 실행·상태 유지·코드 실행·버스트 부하)
- 웹 서비스와 에이전트 워크로드 비교
- 세션 상태 외부화와 체크포인트 기반 재개
- LLM 생성 코드의 샌드박스 격리(마이크로VM·강화 런타임)
- 컨테이너 격리 수준 비교(커널 공유 vs 별도 커널)
- 큐 길이 기반 이벤트 오토스케일링
- 도구 접근 허용 목록과 egress 통제
- CPU 실행 노드와 GPU 추론 노드풀 분리
- 단계별 트레이스·토큰 사용량 관측성

## 4. 연결 기출 토픽과 예상 변형

- **클라우드 네이티브**: 140회 2교시 **서버리스**, 3교시 **클라우드 네이티브 재해복구**(RTO/RPO·Active-Active/Passive·Pilot Light)가 출제됐다. 에이전트 운영은 서버리스의 이벤트 기반 확장과 상태 관리 문제를 함께 다루는 응용 사례다.
- **스토리지**: 140회 3교시 **스토리지 아키텍처 비교**(블록·파일·오브젝트)가 출제됐다. 세션 상태·체크포인트·작업 산출물을 어디에 저장할지가 같은 비교로 이어진다.
- **프로세스 관리**: 140회 1교시 **좀비 프로세스**처럼 OS 기본기도 꾸준히 나온다. 샌드박스 안에서 끝나지 않은 하위 프로세스 정리는 에이전트 실행 환경의 실무 이슈다.
- **멀티에이전트**: 139회 3교시 **다중 에이전트 시스템**(MAS)이 출제됐다. 여러 에이전트를 운영할 때의 자원 격리와 확장 단위 설계로 연결된다.
- **예상 변형**
  - 1교시: "AI 에이전트 실행 환경의 샌드박스(Sandbox) 격리 방식을 비교하시오"
  - 1교시: "상태 저장(Stateful) 워크로드의 컨테이너 운영 고려사항을 설명하시오"
  - 논술: "엔터프라이즈 AI 에이전트 운영을 위한 클라우드 네이티브 플랫폼 아키텍처를 설계하시오"

## 5. 답안 구성 예시

**단답형**(1교시, 1페이지)
- 정의: 계획-도구 호출 루프를 장시간 수행하는 에이전트를 상태 외부화·격리 실행·이벤트 확장으로 운영하는 구조
- 특징 3개: ① 상태 외부화와 체크포인트 재개 ② 생성 코드의 커널 수준 격리 ③ 큐 길이 기반 확장
- 구성도 키워드: 게이트웨이 → 작업 큐 → 에이전트 Pod(상태 저장소) → 샌드박스·도구 게이트웨이·GPU 추론 → 관측성

**논술형(2~4교시) 목차**
1. 개요: 무상태 웹 서비스 전제의 쿠버네티스와 에이전트 워크로드의 불일치
2. 구성/비교: 웹 vs 에이전트 비교표, 운영 구조도, 격리 수준 비교표
3. 적용방안: 상태 외부화·체크포인트, 마이크로VM 샌드박스, 큐 기반 오토스케일, 도구 허용 목록, CPU·GPU 노드풀 분리
4. 고려사항: 샌드박스 기동 지연과 비용, 장기 실행 작업의 배포 중단, 토큰 비용 폭증, 다중 테넌트 격리
5. 기술사 제언: 에이전트를 "오래 사는 요청"이 아니라 **재개 가능한 작업**(Job)으로 모델링하고, 생성 코드 실행은 처음부터 별도 격리 계층으로 분리할 것
