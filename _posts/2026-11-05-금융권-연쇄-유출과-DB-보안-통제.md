## 1. 뉴스 요약

경제타임스(11-03)는 **금융투자업계에 연쇄 정보유출이 이어지며 사이버보안 비상이 걸렸다**고 보도했다. 앞서 브릿지경제(10-27)는 금융감독원장이 **"금융투자업권도 해킹 사고"를 언급하며 금융권 보안 강화를 주문**했다고 전했고, 같은 시기 보안뉴스(10-26)는 **미래에셋생명의 침해사고와 개인정보 유출**을 보도했다. 공격 경로는 다양해도 결국 공격자가 노리는 것은 **고객 정보가 모여 있는 데이터베이스**다. 사고별 유출 경로와 규모는 제목 이상으로 확인되지 않으므로, 아래에서는 **데이터베이스 보안 통제의 구조**를 답안 재료로 정리한다.

## 2. 핵심 개념

### 정의
**데이터베이스 보안**은 DB에 저장된 데이터의 기밀성·무결성·가용성을 지키기 위해 **누가 접근할 수 있는지(접근통제), 데이터를 읽혀도 쓸 수 없게(암호화), 누가 무엇을 했는지 남기고 이상을 찾는(감사·모니터링)** 세 가지 통제를 겹겹이 적용하는 활동이다. 네트워크·서버 보안이 뚫린 뒤에도 피해를 줄이는 **마지막 방어선**이라는 점에서 금융권 유출 사고 대응의 핵심이다.

### 구성도 — DB 보안 다층 통제

```
 사용자·애플리케이션·DBA
        │
        ▼
 ┌─ 접근통제 ───────────────────────────────────────────────┐
 │ 계정·권한 최소화 · 접근 경로 통제(게이트웨이/에이전트)     │
 │ 시간·IP·SQL 유형별 정책 · 대량 조회 차단 · 결재 연동       │
 └──────────────────────┬──────────────────────────────────┘
                        ▼
 ┌─ 데이터베이스 ───────────────────────────────────────────┐
 │ 암호화: 주민번호·계좌번호 등 컬럼 암호화 / 저장 파일 암호화 │
 │ 키 관리: 키와 데이터 분리 보관(HSM·KMS)                    │
 └──────────────────────┬──────────────────────────────────┘
                        ▼
 ┌─ 감사·모니터링 ──────────────────────────────────────────┐
 │ 접속기록 보관 · DB 활동 모니터링(DAM) · 이상 행위 탐지      │
 │ (평소와 다른 시간·대량 조회·권한 변경)                    │
 └─────────────────────────────────────────────────────────┘
```

### DB 접근제어 구축 방식 비교

| 방식 | 구조 | 장점 | 단점 |
|---|---|---|---|
| 게이트웨이(프록시) | 사용자와 DB 사이에 통제 서버 경유 | 강력한 차단, DB 부하 없음 | 우회 접속 통제 필요, 단일 장애점 |
| 에이전트 | DB 서버에 에이전트 설치 | 우회 없음, 로컬 접속도 통제 | DB 서버 부하, 설치 부담 |
| 스니핑 | 네트워크 트래픽 복제 분석 | 성능 영향 없음 | 차단 불가(감시만), 암호화 트래픽 한계 |
| 하이브리드 | 게이트웨이 + 에이전트 결합 | 통제 범위 최대화 | 구축·운영 복잡도 |

### DB 암호화 방식 비교

| 방식 | 암호화 위치 | 장점 | 단점 |
|---|---|---|---|
| API 방식 | 애플리케이션에서 암·복호화 | DB 부하 적음, 세밀한 통제 | 애플리케이션 수정 필요 |
| 플러그인 방식 | DB 내부 함수·뷰로 처리 | 애플리케이션 수정 최소 | DB 부하 증가 |
| TDE(투명 데이터 암호화) | DB 엔진이 저장 시 자동 암호화 | 애플리케이션 수정 없음, 성능 우수 | 정상 접속자에게는 평문 노출 |
| 파일 암호화 | OS 파일 단위 | 비정형 데이터까지 보호 | 세밀한 접근 통제 어려움 |
| 하이브리드 | 컬럼(API·플러그인) + TDE 결합 | 위험도별 차등 보호 | 키 관리 복잡 |

TDE는 저장 매체 탈취에는 강하지만, **권한을 가진 계정이 탈취되면 평문이 그대로 조회**된다. 그래서 주민번호·계좌번호 같은 핵심 컬럼은 **컬럼 단위 암호화 + 접근통제**를 함께 쓰는 것이 일반적이다.

### DB 활동 모니터링(DAM)이 잡아야 할 이상 행위
- 업무 시간 외 대량 조회, 평소 접근하지 않던 테이블 조회
- 관리자 권한 부여·계정 생성 같은 권한 변경
- 감사 로그 삭제·비활성화 시도
- 애플리케이션 계정이 아닌 개인 계정의 직접 접속
- 짧은 시간 내 반복적인 전체 테이블 조회(덤프 시도)

### 관련 법·기준
- **개인정보의 안전성 확보조치 기준**(개인정보보호위원회 고시): 접근권한 관리, 접근통제, 암호화, 접속기록 보관·점검(일반적으로 1년 이상, 대규모·민감정보 처리 시스템은 2년 이상)
- **개인정보 보호법 제24조의2**: 주민등록번호 암호화 의무
- **전자금융감독규정**: 금융회사의 정보처리시스템 보호·접근통제 요구
- **ISMS-P**: 접근통제·암호화·로그 관리 인증 기준

## 3. 기술사 출제 포인트

- DB 보안 3대 통제(접근통제·암호화·감사)와 다층 방어
- DB 접근제어 구축 방식(게이트웨이·에이전트·스니핑·하이브리드) 비교
- DB 암호화 방식(API·플러그인·TDE·파일) 비교
- TDE의 한계와 컬럼 암호화 병행 필요성
- 암호키 관리(HSM·KMS, 키와 데이터 분리)
- DB 활동 모니터링(DAM)과 이상 행위 탐지
- 접속기록 보관·점검 의무(안전성 확보조치 기준)
- 주민등록번호 암호화 의무
- 금융권 DB 보안 규제(전자금융감독규정·ISMS-P)

## 4. 연결 기출 토픽과 예상 변형

- **분산 DB**: 139회 1교시 **분산 DB 투명성**이 출제됐다. 데이터가 여러 노드에 분산될수록 접근통제·암호화 정책을 일관되게 적용하는 것이 과제가 된다.
- **컴플라이언스**: 140회 4교시 **정보보호 컴플라이언스**가 출제됐다. 안전성 확보조치 기준의 DB 관련 항목은 컴플라이언스 문항의 구체 예시다.
- **가명처리**: 139회 1교시 **개인정보보호를 위한 가명처리 기법**이 출제됐다. 운영 DB의 암호화와 분석용 데이터의 가명처리를 구분해 쓰면 답안이 정확해진다.
- **포렌식**: 140회 1교시 **디지털 포렌식**이 출제됐다. DB 접속기록과 감사 로그는 유출 사고 조사의 핵심 증거다.
- **예상 변형**
  - 1교시: "DB 암호화 방식(API·Plug-in·TDE)을 비교하시오"
  - 1교시: "DB 접근제어 솔루션의 구축 방식을 비교하시오"
  - 논술: "금융권 개인정보 유출 방지를 위한 데이터베이스 보안 체계를 접근통제·암호화·감사 관점에서 제시하시오"

## 5. 답안 구성 예시

**단답형**(1교시, 1페이지)
- 정의: 접근통제·암호화·감사를 겹겹이 적용해 DB 데이터의 기밀성·무결성·가용성을 지키는 활동
- 특징 3개: ① 침해 이후 마지막 방어선 ② 위험도별 암호화 방식 차등 ③ 접속기록 기반 사후 추적
- 구성도 키워드: 사용자 → 접근통제(게이트웨이·에이전트) → DB(컬럼 암호화·TDE·키 관리) → 감사·DAM

**논술형(2~4교시) 목차**
1. 개요: 금융권 연쇄 유출과 DB 중심 보호의 필요성
2. 구성/비교: 다층 통제 구성도, 접근제어 방식 비교표, 암호화 방식 비교표
3. 적용방안: 핵심 컬럼 암호화 + TDE, 게이트웨이·에이전트 하이브리드 통제, 대량 조회 차단, DAM 이상 탐지, 키 HSM 보관
4. 고려사항: 성능 영향, 애플리케이션 수정 범위, 관리자 계정 통제, 로그 위·변조 방지
5. 기술사 제언: 유출 사고의 대부분이 **정상 계정 탈취·내부자**에서 시작된다는 전제로, 암호화보다 **계정별 조회량 통제와 이상 행위 탐지**를 우선순위에 두고 접속기록 점검을 자동화할 것
