## 1. 뉴스 요약

지티티코리아(11-14)는 **AI 코드 검증 속도를 따라가지 못한 기업이 76%에 이르러 보안·품질 위험을 막을 자동 검증이 시급하다**고 보도했고, 지디넷코리아(11-16)는 **현대오토에버가 SI·ITO 사업에서 바이브코딩과 AI 에이전트 개발을 추진**한다고 전했다. 전자신문(11-21)은 소프트웨어 산업 전시회 '소프트웨이브 2026'을 앞두고 AI 혁신과 SW 산업의 변화를 다뤘다. AI로 코드를 빨리 만드는 것과 **그 코드가 안정적으로 사용자에게 전달되는 것은 다른 문제**라는 인식이 퍼지고 있다. 이 글은 특정 기사 하나가 아니라 최근 AI 코딩 확산 흐름을 바탕으로, 소프트웨어 딜리버리 성과를 재는 **DORA 지표**를 토픽 심화로 정리한다.

## 2. 핵심 개념

### 정의
**DORA 지표**는 구글 산하 DORA(DevOps Research and Assessment) 연구 프로그램이 대규모 설문 연구로 도출한 **소프트웨어 딜리버리 성과 측정 지표**다. 변경이 얼마나 빨리 나가는지를 보는 **처리량**(Throughput)과, 나간 변경이 얼마나 문제없이 운영되는지를 보는 **안정성**(Stability)을 함께 측정한다. 두 축을 동시에 보는 이유는, 속도만 재면 품질이 무너지고 안정성만 재면 변경이 멈추기 때문이다.

### DORA 지표 구성

| 지표 | 축 | 의미 | 측정 방법 | 개선 수단 |
|---|---|---|---|---|
| 배포 빈도 | 처리량 | 운영 환경에 얼마나 자주 배포하는가 | 기간당 운영 배포 횟수 | 작은 단위 배포, 배포 자동화 |
| 변경 리드타임 | 처리량 | 커밋부터 운영 반영까지 걸린 시간 | 커밋 시각–배포 시각 차이 | CI 속도 개선, 승인 대기 축소 |
| 변경 실패율 | 안정성 | 배포 중 장애·롤백·긴급 수정을 일으킨 비율 | 실패 배포 수 / 전체 배포 수 | 자동 테스트, 점진적 배포 |
| 배포 실패 복구 시간 | 안정성 | 실패한 배포로 인한 장애를 복구하는 데 걸린 시간 | 장애 발생–복구 시각 차이 | 롤백 자동화, 관측성, 기능 플래그 |
| 재작업률 | 안정성 | 계획에 없던 수정 배포의 비율 | 장애 대응성 배포 / 전체 배포 | 품질 게이트, 원인 분석 |

복구 시간은 예전에는 서비스 복구 시간(MTTR)으로 불렸고, 최근 보고서에서는 **배포로 인한 실패의 복구 시간**으로 범위를 좁혔다. 재작업률은 최근 추가된 지표로, 변경 실패율이 놓치는 "작은 수정 배포의 반복"을 잡아낸다.

### 구성도 ① — 딜리버리 파이프라인과 측정 지점

```
 [커밋] ──▶ [CI 빌드·테스트] ──▶ [코드 리뷰·승인] ──▶ [스테이징] ──▶ [운영 배포]
   │                                                                  │
   └────────────────── 변경 리드타임 ─────────────────────────────────┘
                                                                      │
                                                     배포 빈도(기간당 횟수)
                                                                      │
                                                                      ▼
                                                        [운영 모니터링]
                                                          │        │
                                         정상 ◀───────────┘        └──▶ 실패(장애·롤백)
                                                                         │
                                                         변경 실패율 · 재작업률
                                                                         │
                                                                         ▼
                                                              [복구] ── 복구 시간
```

데이터는 **저장소·CI/CD 도구·장애 관리 도구**에서 각각 커밋·배포·인시던트 기록을 자동으로 모아야 한다. 사람이 손으로 집계하면 지표가 부정확해지고 측정 자체가 부담이 된다.

### 처리량과 안정성은 상충하는가
DORA 연구의 대표적인 결론은 **잘하는 조직은 둘 다 잘한다**는 것이다. 작은 변경을 자주 배포하면 한 번의 변경 범위가 작아 실패 확률이 낮고, 실패해도 원인을 찾기 쉬워 복구가 빠르다. 반대로 변경을 모아 드물게 배포하면 한 번에 많은 것이 바뀌어 실패가 커지고 복구도 오래 걸린다.

| 구분 | 큰 배치·드문 배포 | 작은 배치·잦은 배포 |
|---|---|---|
| 배포 단위 | 수주~수개월 변경 묶음 | 하루 수회~수일 단위 |
| 실패 시 원인 파악 | 어려움(변경이 많음) | 쉬움(변경이 적음) |
| 롤백 범위 | 큼 | 작음 |
| 리드타임 | 김 | 짧음 |
| 필요한 기반 | 수동 검증 위주 | 자동 테스트·자동 배포·관측성 |
| 조직 문화 | 변경을 위험으로 봄 | 변경을 일상으로 봄 |

### 측정 프레임워크 비교

| 구분 | DORA 지표 | SPACE 프레임워크 | 전통 생산성 지표 |
|---|---|---|---|
| 초점 | 딜리버리 성과(속도·안정성) | 개발자 생산성의 다차원 | 산출량 |
| 구성 | 배포 빈도·리드타임·실패율·복구 시간·재작업률 | 만족·성과·활동·소통·효율 | 코드 줄 수, 커밋 수, 기능점수 |
| 측정 단위 | 팀·서비스 | 개인·팀·조직 | 개인 |
| 강점 | 객관적·자동 수집 가능 | 사람·협업 요소 포함 | 단순 |
| 약점 | 개발자 경험을 놓침 | 설문 의존, 측정 비용 | 왜곡 쉬움(줄 수 늘리기) |

### AI 코딩 도구와 DORA 지표
AI 코딩 도구는 코드 작성 시간을 줄이지만, DORA 연구에서는 **AI 도입이 늘수록 딜리버리 안정성이 떨어지는 경향**도 보고된 바 있다. 원인으로는 다음이 꼽힌다.
- **변경 단위 비대화**: 한 번에 많은 코드가 생성돼 작은 배치 원칙이 깨진다.
- **리뷰 병목**: 코드 생산은 빨라졌지만 리뷰·테스트 용량은 그대로라 리드타임이 오히려 늘어난다.
- **이해 부족**: 이해하지 못한 코드가 장애를 일으키면 복구 시간이 길어진다.

따라서 AI 도입 효과는 "코드를 얼마나 많이 만들었나"가 아니라 **DORA 지표가 실제로 좋아졌는가**로 판단해야 한다. 생산량이 늘었는데 변경 실패율·재작업률이 올라가면 개선이 아니라 위험이 늘어난 것이다.

### 구성도 ② — 지표 기반 개선 루프

```
 [측정]  파이프라인·인시던트 데이터 자동 수집 → 5개 지표 산출
    │
    ▼
 [진단]  병목 찾기 — 리드타임 중 대기 시간? 테스트 시간? 승인 대기?
    │
    ▼
 [개선]  배치 축소 · 테스트 자동화 · 점진적 배포(카나리·블루그린) · 기능 플래그
    │
    ▼
 [검증]  지표 추세 확인 — 처리량과 안정성이 함께 좋아졌는가
    │
    └──────▶ [측정]으로 반복
```

### 측정의 함정
- **굿하트의 법칙**: 지표가 목표가 되면 왜곡된다. 배포 빈도를 늘리려고 의미 없는 배포를 쪼개는 식이다.
- **팀 간 순위 매기기**: 서비스 특성이 다른 팀을 같은 숫자로 비교하면 협력이 무너진다. 같은 팀의 추세를 본다.
- **개인 평가 사용**: DORA는 팀·시스템 성과 지표다. 개인 평가에 쓰면 측정 데이터가 오염된다.
- **한 축만 보기**: 처리량만 보거나 안정성만 보면 반대 축이 무너진다.

### 관련 기준
- **ISO/IEC/IEEE 32675**: DevOps 구축·운영 요구사항 표준
- **ISO/IEC/IEEE 12207**: 소프트웨어 생명주기 프로세스
- **ITIL 4**: 변경 활성화(Change Enablement)·인시던트 관리 관행
- **SRE의 SLO·오류 예산**: 안정성 목표를 넘으면 배포 속도를 늦추는 운영 원칙

## 4. 연결 기출 토픽과 예상 변형

- **DevOps**: 블로그 통합 기출 분석(`exam_trend_integrated.json`) 기준 **DevOps는 기출 8회, 최근 출제 빈도**(recent 7)도 높은 소프트웨어공학 키워드다. DORA 지표는 DevOps 성과를 정량화하는 표준 답안 재료다.
- **무중단 배포**: 139회 1교시에 **SW 무중단 배포**가 출제됐다. 블루그린·카나리 배포가 변경 실패율과 복구 시간을 어떻게 줄이는지 DORA 지표로 설명하면 답안이 깊어진다.
- **기술부채**: 139회 3교시에 **기술부채**가 출제됐다. 재작업률 상승은 기술부채가 쌓이고 있다는 정량 신호다.
- **예상 변형**
  - 1교시: "DORA 4대 지표를 설명하시오"
  - 1교시: "SPACE 프레임워크를 설명하시오"
  - 논술: "생성형 AI 코딩 도구 도입 효과를 측정하기 위한 소프트웨어 딜리버리 성과 관리 방안을 제시하시오"

## 5. 답안 구성 예시

**단답형**(1교시, 1페이지)
- 정의: 소프트웨어 딜리버리 성과를 처리량(배포 빈도·변경 리드타임)과 안정성(변경 실패율·복구 시간·재작업률)으로 측정하는 지표
- 특징 3개: ① 처리량과 안정성 동시 측정 ② 파이프라인·인시던트 데이터로 자동 수집 ③ 팀·시스템 단위 추세 관리
- 구성도 키워드: 커밋 → CI → 리뷰 → 배포(리드타임·빈도) → 운영(실패율·재작업률) → 복구(복구 시간)

**논술형(2~4교시) 목차**
1. 개요: AI 코딩 확산과 딜리버리 안정성 문제
2. 구성/비교: 지표 구성표, 파이프라인 측정 구성도, 배치 크기 비교표, DORA·SPACE 비교표
3. 적용방안: 지표 자동 수집, 작은 배치·트렁크 기반 개발, 테스트 자동화, 점진적 배포, 리뷰 용량 확충, SLO·오류 예산
4. 고려사항: 굿하트의 법칙, 팀 간 비교 금지, 개인 평가 오용, 레거시 시스템의 측정 어려움
5. 기술사 제언: AI 도입 성과를 코드 생산량이 아닌 **DORA 지표의 처리량·안정성 동시 개선**으로 검증하고, 안정성 지표가 나빠지면 AI 활용 범위와 리뷰 기준부터 조정할 것
