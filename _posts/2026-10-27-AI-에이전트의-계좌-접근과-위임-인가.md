## 1. 뉴스 요약

CBC뉴스(10-24)는 "**[AI 계좌접근 비상] 승인 없는 자금 이동 우려… 美 대형은행, AI 계좌 접근 막는다**"는 제목으로, 미국 대형은행들이 고객 대신 금융 업무를 처리하는 AI 에이전트의 계좌 접근을 제한하고 있다고 보도했다. 사용자가 에이전트에게 맡긴 일이 **사용자가 의도하지 않은 송금**으로 이어질 수 있다는 우려가 배경이다. Vietnam.vn(10-22)도 "**AI는 스마트 뱅킹의 길을 열지만 보안을 희생해서는 안 된다**"는 논조의 기사를 실었다. 은행별 조치 내용은 제목 이상으로 확인되지 않으므로, 아래에서는 AI 에이전트에게 금융 권한을 **안전하게 위임하는 구조**를 답안 재료로 정리한다.

## 2. 핵심 개념

### 정의
**위임 인가**(Delegated Authorization)는 사용자가 자신의 비밀번호를 넘기지 않고, **제3자(앱·AI 에이전트)에게 정해진 범위와 기간 안에서만 자원 접근 권한을 부여**하는 방식이다. AI 에이전트는 사람이 아니면서 시스템에 접근하는 주체, 즉 **비인간 신원**(NHI, Non-Human Identity)이므로, 사람 계정과 분리된 신원·권한·감사 체계가 필요하다.

### 접근 방식 비교 — 스크래핑 vs API 위임

| 구분 | 화면 스크래핑(자격증명 공유) | API 위임 인가(OAuth 등) |
|---|---|---|
| 접근 방법 | 사용자 ID·비밀번호로 로그인해 화면 조작 | 사용자가 승인한 토큰으로 API 호출 |
| 비밀번호 노출 | 에이전트가 보관(유출 위험) | 노출 없음 |
| 권한 범위 | 사용자와 동일한 전체 권한 | 조회·이체 등 범위(scope) 제한 |
| 기간 | 비밀번호 변경 전까지 무기한 | 짧은 만료 + 갱신·철회 가능 |
| 은행의 식별 | 사람인지 에이전트인지 구분 불가 | 어떤 에이전트인지 식별 가능 |
| 감사·책임 | 사용자 행위와 구분 불가 | 에이전트 행위로 기록·추적 |
| 은행 입장 | 이상거래로 차단 대상 | 통제 가능한 접근으로 허용 가능 |

은행이 "AI 접근을 막는다"고 할 때 실제로 문제가 되는 것은 대개 **왼쪽 열**이다. 사람과 구분되지 않는 무제한 접근은 막고, 오른쪽 열처럼 통제 가능한 경로를 따로 여는 것이 보안 설계의 방향이다.

### 구성도 — 에이전트 금융 거래 위임 흐름

```
 사용자 ──① "월세 자동 이체 맡길게"──▶ AI 에이전트
   │                                       │
   │ ② 동의 화면: 범위(조회·이체), 한도(100만 원), 기간(30일), 수취인 제한
   ▼                                       │
 은행 인가 서버 ──③ 접근 토큰(짧은 만료, 범위 제한, 에이전트 ID 포함)──▶ 에이전트
                                           │
                                 ④ API 호출: 이체 요청
                                           ▼
 은행 API 게이트웨이 ─ 정책 검사: 범위 내? 한도 내? 등록 수취인?
        │          └ 위험도 높음(신규 수취인·고액) → ⑤ 사용자 단계적 인증(Step-up)
        ▼
 거래 실행 ─▶ ⑥ 감사 로그(누가·어떤 에이전트로·무엇을) ─▶ 사용자 알림
                                           │
 사용자 ──⑦ 언제든 권한 철회(Revoke)────────┘
```

### 에이전트 고유 위협과 통제

| 위협 | 시나리오 | 통제 |
|---|---|---|
| 프롬프트 인젝션 | 청구서·메일에 숨긴 지시로 송금 유도 | 고위험 거래는 사람 확인, 수취인 화이트리스트 |
| 과잉 권한 | 조회만 필요한데 이체 권한까지 부여 | 최소 권한 범위(scope), 기능별 토큰 분리 |
| 토큰 탈취 | 에이전트 서버 침해로 토큰 유출 | 짧은 만료, 송신자 제약 토큰, 이상 사용 탐지 |
| 신원 위장 | 악성 에이전트가 정상 에이전트로 위장 | 에이전트 등록·인증서, 클라이언트 인증 |
| 연쇄 위임 | 에이전트가 다른 에이전트에 권한 재위임 | 위임 체인 기록(actor 정보), 재위임 제한 |
| 책임 공백 | 오송금 시 사용자·에이전트·은행 책임 불명확 | 동의 기록·감사 로그, 약관상 책임 분담 |

### NHI 관리 관점
- **등록**: 에이전트마다 고유 신원을 부여하고 소유자(사용자·기업)를 연결한다.
- **수명주기**: 발급 → 사용 → 갱신 → 철회. 쓰지 않는 에이전트 자격증명은 자동 만료시킨다.
- **가시성**: 사람 계정과 분리해 "이 거래는 에이전트가 했다"를 로그에서 구분한다.
- **이상 행위 탐지**: 사람과 다른 에이전트 특유의 패턴(호출 빈도·시간대)을 기준선으로 삼는다.

### 관련 표준·법
- **OAuth 2.0**(RFC 6749): 위임 인가 표준. 범위·만료·철회의 기본 틀
- **OAuth 2.0 토큰 교환**(RFC 8693): 다른 주체를 대신해 행동할 때 위임 관계(actor)를 토큰에 표현
- **FAPI 2.0**(OpenID 재단): 금융 등 고보안 API용 OAuth 보안 프로파일
- **국내 마이데이터**: 신용정보법에 따라 표준 API 방식으로 정보를 전송하며, 마이데이터 서비스에서는 스크래핑 방식을 쓰지 않도록 했다
- **전자금융거래법 제9조**: 접근매체 위·변조나 무권한 거래 사고 시 금융회사 책임 원칙, 이용자 고의·중과실 시 예외 — 에이전트 위임 사고의 책임 분담 쟁점

## 3. 기술사 출제 포인트

- 위임 인가의 정의와 자격증명 공유(스크래핑) 방식의 위험
- 비인간 신원(NHI)으로서 AI 에이전트의 신원·권한 관리
- OAuth 범위(scope) 최소화와 짧은 만료·철회
- 토큰 교환(RFC 8693)을 통한 위임 체인 표현
- 고위험 거래의 단계적 인증(Step-up)과 사람 확인
- 프롬프트 인젝션에 의한 무권한 송금 위협과 대응
- 거래 한도·수취인 제한 등 정책 기반 API 게이트웨이
- 에이전트 행위 감사 로그와 책임 분담
- 마이데이터 API 전환과 스크래핑 금지 사례
- 전자금융거래법상 무권한 거래 책임 원칙

## 4. 연결 기출 토픽과 예상 변형

- **비인간 신원**(NHI): 140회 1교시에 **NHI(Non-Human Identities) 보안 취약점**이 출제됐다. AI 에이전트 계좌 접근은 NHI 문항의 가장 구체적인 사례로, 같은 개념이 "AI 에이전트 권한 관리"로 확장돼 나올 수 있다.
- **AI 통제 상실**: 140회 2교시 **AI 보안 — 자율성으로 인한 통제 상실 위협 및 대응**이 출제됐다. 사용자가 의도하지 않은 송금은 통제 상실의 금융 사례다.
- **마이데이터**: 블로그 통합 기출 분석(`exam_trend_integrated.json`) 기준 **마이데이터는 기출 5회**인 빈출 키워드다. 스크래핑에서 API로의 전환 경험은 에이전트 접근 통제의 선례로 쓸 수 있다.
- **멀티에이전트**: 139회 3교시 **다중 에이전트 시스템**(MAS)이 출제됐다. 에이전트 간 재위임 통제는 MAS 보안 고려사항과 이어진다.
- **예상 변형**
  - 1교시: "OAuth 2.0 기반 위임 인가의 개념과 AI 에이전트 적용 시 고려사항을 설명하시오"
  - 1교시: "AI 에이전트의 비인간 신원(NHI) 관리 방안을 설명하시오"
  - 논술: "AI 에이전트가 금융 거래를 대행하는 환경의 보안 위협과 인가·인증·감사 체계를 제시하시오"

## 5. 답안 구성 예시

**단답형**(1교시, 1페이지)
- 정의: 비밀번호 공유 없이 제3자에게 범위·기간이 제한된 권한을 부여하는 방식, AI 에이전트는 NHI로 관리
- 특징 3개: ① 범위·한도·기간 제한 토큰 ② 고위험 거래 단계적 인증 ③ 에이전트 식별 감사 로그와 철회
- 구성도 키워드: 사용자 동의 → 인가 서버 토큰 발급 → API 게이트웨이 정책 검사 → Step-up → 실행·로그 → 철회

**논술형(2~4교시) 목차**
1. 개요: AI 에이전트 금융 대행 확산과 은행의 접근 차단 움직임
2. 구성/비교: 스크래핑 vs API 위임 비교표, 위임 흐름 구성도, 위협·통제표
3. 적용방안: 에이전트 등록·인증, 최소 범위 토큰, 거래 한도·수취인 제한, Step-up 인증, 감사 로그
4. 고려사항: 프롬프트 인젝션, 연쇄 위임, 사용자 경험 저하, 사고 시 책임 분담
5. 기술사 제언: 에이전트 접근을 일괄 차단하기보다 **식별 가능한 API 위임 경로를 표준화**해 열고, 고위험 거래는 사람 확인을 필수로 남기며, NHI를 사람 계정과 분리해 수명주기 관리할 것
