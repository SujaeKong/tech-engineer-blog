## 1. 뉴스 요약

이데일리·지디넷코리아·한겨레·아이티데일리 등(10-26)은 **기업용 소프트웨어 업체 더존비즈온에서 개발서버 침해사고가 발생**했고, **과학기술정보통신부가 민관합동조사단을 꾸려 조사에 착수**했다고 보도했다. 더테크(10-26)는 **두 차례 침해**가 있었고 정부가 **고객사 피해 확산을 우려**해 합동조사를 결정했다고 전했으며, 충청시사신문(10-26)은 정부가 이를 **'중대 사고'로 규정**했다고 보도했다. 지디넷코리아(10-26)는 회사가 **후속 조치로 160억 원 규모의 보안 투자**를 공개했다고 전했다. 침해 경로와 유출 범위는 제목 이상으로 확인되지 않으므로, 아래에서는 **소프트웨어 개발환경이 공급망 공격의 출발점이 되는 구조**와 대응 체계를 정리한다.

## 2. 핵심 개념

### 정의
**SW 개발환경 보안**은 소스코드 저장소, 빌드·배포 파이프라인(CI/CD), 아티팩트 저장소, 코드 서명 키, 개발용 데이터처럼 **소프트웨어가 만들어지는 과정의 자산을 보호해, 배포되는 소프트웨어의 무결성과 고객 환경의 안전을 지키는 활동**이다. 많은 고객사가 쓰는 소프트웨어의 공급사가 뚫리면 피해가 고객 전체로 번지므로, 개발환경 침해는 단일 기업 사고가 아니라 **SW 공급망 사고**로 다뤄진다.

### 구성도 — 개발환경 자산과 공격 경로

```
 개발자 PC ──커밋──▶ [소스 저장소] ──트리거──▶ [CI/CD 빌드 서버]
    │                    │                         │
    │ ① 계정 탈취        │ ② 소스 유출 →          │ ③ 빌드 변조 →
    │   (피싱·토큰)      │   취약점 분석·재사용    │   악성코드 삽입
    ▼                    ▼                         ▼
 [비밀정보]          [개발·테스트 DB]           [아티팩트 저장소] ──서명──▶ 배포
 API 키·접속 정보     ④ 실데이터 혼입 시         ⑤ 서명 키 탈취 →          │
 하드코딩 유출          개인정보 유출            정상 서명된 악성 업데이트   ▼
                                                                    [고객사 환경]
                                                               ⑥ 업데이트 경로로 확산
```

①~③은 공격자가 "만드는 과정"을 장악하는 단계이고, ⑤~⑥은 그 결과가 **정상 업데이트의 형태로 고객에게 도달**하는 단계다. 2020년 SolarWinds 사건이 빌드 단계 변조로 다수 고객 기관에 악성 업데이트가 배포된 대표 사례다.

### 운영 서버 보안 vs 개발환경 보안

| 구분 | 운영(프로덕션) 서버 | 개발환경 |
|---|---|---|
| 보호 대상 | 서비스·고객 데이터 | 소스·빌드·서명 키·개발 데이터 |
| 일반적 보안 수준 | 높음(관제·접근통제 집중) | 상대적으로 낮음(편의 우선) |
| 접근 주체 | 운영자 소수 | 개발자·외주·자동화 계정 다수 |
| 침해 영향 | 해당 서비스 중단·유출 | 배포 SW를 통한 고객 전체 확산 |
| 탐지 난이도 | 이상 트래픽으로 탐지 가능 | 정상 커밋·빌드와 구분 어려움 |
| 주요 통제 | 방화벽·IPS·DB 접근제어 | 저장소 권한·빌드 격리·서명·비밀 관리 |

### 개발 단계별 보안 통제

| 단계 | 위협 | 통제 |
|---|---|---|
| 코드 작성 | 계정 탈취, 비밀정보 하드코딩 | MFA, 비밀정보 스캐닝, 비밀 관리 금고(Vault) |
| 형상관리 | 무단 커밋·이력 변조 | 커밋 서명, 브랜치 보호, 2인 코드 리뷰 |
| 빌드 | 빌드 서버 변조, 의존성 오염 | 격리된 일회성 빌드, 의존성 고정·검증, SBOM 생성 |
| 패키징·서명 | 서명 키 탈취 | HSM 보관, 서명 권한 분리, 출처 증명(Provenance) |
| 배포 | 악성 업데이트 유포 | 고객 측 서명 검증, 단계적 배포, 무결성 모니터링 |
| 개발 데이터 | 실데이터 유출 | 가명·합성 데이터 사용, 운영망과 분리 |

### SLSA 빌드 수준
**SLSA**(Supply-chain Levels for Software Artifacts)는 빌드 무결성을 단계로 정의한 프레임워크다.
- **Build L1**: 빌드 과정의 출처 정보(Provenance) 기록
- **Build L2**: 호스팅된 빌드 플랫폼이 출처 정보에 서명
- **Build L3**: 빌드 간 격리, 서명 키를 빌드 작업이 접근할 수 없도록 보호 — 빌드 변조를 어렵게 함

### 관련 표준·기준
- **NIST SP 800-218 SSDF**: 보안 SW 개발 프레임워크(조직 준비·SW 보호·안전한 SW 생산·취약점 대응 4개 실천군)
- **SLSA v1.0**: 빌드 무결성 수준 정의
- **SW 공급망 보안 가이드라인**(과기정통부·국정원·KISA, 2024): SBOM 활용 등 국내 공급망 보안 권고
- **정보통신망법**: 침해사고 신고 의무, 중대한 침해사고 시 민관합동조사단 구성 근거

## 3. 기술사 출제 포인트

- SW 개발환경 자산(소스·CI/CD·아티팩트·서명 키·개발 데이터)
- 개발환경 침해가 공급망 사고로 번지는 경로
- 빌드 변조·서명 키 탈취와 정상 서명된 악성 업데이트
- 형상관리 무결성(커밋 서명·브랜치 보호·코드 리뷰)
- SLSA 빌드 수준(L1~L3)과 출처 증명(Provenance)
- NIST SSDF 4개 실천군
- 비밀정보 하드코딩 방지와 비밀 관리
- 개발·테스트 데이터의 가명·합성 처리
- SBOM 기반 고객사 영향 분석
- 민관합동조사 등 중대 침해사고 대응 체계

## 4. 연결 기출 토픽과 예상 변형

- **형상관리**: 140회 4교시에 **소프트웨어 형상관리**(SCM)가 출제됐다. 형상관리의 목적에 "무결성 보장"이 들어가는 만큼, 개발 저장소 침해는 형상관리 통제(접근권한·변경 이력·서명)의 실패 사례로 쓸 수 있다.
- **SW 공급망**: 140회 2교시 **AI 생성 소스코드·오픈웨이트 모델 활용 시 오픈소스 라이선스 리스크**가 SW 공급망 관점으로 출제됐다. 공급망을 라이선스가 아닌 **보안·무결성** 측면에서 묻는 변형이 자연스럽다.
- **배포**: 139회 1교시 **SW 무중단 배포**가 출제됐다. 단계적 배포(카나리)는 악성 업데이트의 확산 범위를 줄이는 보안 통제이기도 하다.
- **합성데이터**: 140회 3교시 **합성데이터 생성·품질 평가**가 출제됐다. 개발·테스트에 실데이터 대신 합성데이터를 쓰는 것은 개발환경 유출 피해를 줄이는 대표 방안이다.
- **예상 변형**
  - 1교시: "SLSA(Supply-chain Levels for Software Artifacts)를 설명하시오"
  - 1교시: "CI/CD 파이프라인의 보안 위협과 대응 방안을 설명하시오"
  - 논술: "SW 공급사의 개발환경 침해가 고객사로 확산되는 경로를 설명하고, 보안 개발 체계(SSDF·SLSA·SBOM) 기반 대응 방안을 제시하시오"

## 5. 답안 구성 예시

**단답형**(1교시, 1페이지)
- 정의: 소스·빌드·서명·개발 데이터 등 SW 생산 과정 자산을 보호해 배포 SW의 무결성을 지키는 활동
- 특징 3개: ① 침해 시 고객 전체로 확산(공급망) ② 정상 활동과 구분 어려운 탐지 난이도 ③ 형상관리·빌드·서명 단계별 통제
- 구성도 키워드: 개발자 → 저장소 → CI/CD → 아티팩트·서명 → 배포 → 고객 (단계별 공격 ①~⑥)

**논술형(2~4교시) 목차**
1. 개요: 기업용 SW 공급사 개발서버 침해와 고객사 확산 우려
2. 구성/비교: 공격 경로 구성도, 운영 vs 개발환경 보안 비교표, 단계별 통제표
3. 적용방안: SLSA L3 수준 빌드 격리·서명 키 HSM 보관, 커밋 서명·브랜치 보호, 비밀정보 스캐닝, 합성 테스트 데이터, SBOM 기반 고객 영향 분석
4. 고려사항: 개발 생산성 저하, 외주·자동화 계정 관리, 오픈소스 의존성, 사고 시 고객 통지 범위
5. 기술사 제언: 개발환경을 **운영환경과 같은 등급의 보호 대상**으로 재분류하고, 사고 시 "어떤 버전이 어느 고객에 배포됐는지"를 즉시 답할 수 있도록 SBOM·출처 증명을 평소에 갖출 것
