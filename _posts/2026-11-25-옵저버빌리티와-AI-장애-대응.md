## 1. 뉴스 요약

연합뉴스·더팩트·서울경제TV 등(11-24)은 **LG유플러스가 AI 통화앱 '익시오' 운영에 데이터독의 AI 기능을 적용해 장애 해결 시간을 85% 단축**했다고 보도했다. 마이크로서비스와 클라우드로 쪼개진 서비스에서는 한 번의 장애에도 수십 개 구성요소가 얽혀, **어디가 원인인지 찾는 데 대부분의 시간이 든다**. 그래서 시스템 내부 상태를 데이터로 들여다보는 옵저버빌리티와, 그 데이터를 AI로 분석해 원인을 좁히는 방식이 운영의 핵심이 되고 있다. 85% 단축의 측정 기준과 적용 기능은 제목 이상으로 확인되지 않으므로, 아래에서는 **옵저버빌리티와 AI 기반 장애 대응 체계**를 정리한다.

## 2. 핵심 개념

### 정의
**옵저버빌리티**(Observability, 관측 가능성)는 시스템이 밖으로 내보내는 **메트릭·로그·트레이스 같은 텔레메트리만으로 내부 상태를 추론하고, 미리 예상하지 못한 문제의 원인까지 찾아낼 수 있는 능력**이다. 정해진 지표가 임계값을 넘는지 감시하는 **모니터링**이 "무엇이 잘못됐는가"를 알려 준다면, 옵저버빌리티는 "**왜** 잘못됐는가"를 묻고 답할 수 있게 해 준다.

### 모니터링 vs 옵저버빌리티

| 구분 | 모니터링 | 옵저버빌리티 |
|---|---|---|
| 질문 | 시스템이 정상인가 | 왜 이렇게 동작하는가 |
| 대상 문제 | 예상한 장애(알려진 문제) | 예상 못 한 장애(미지의 문제) |
| 데이터 | 사전 정의 지표·임계값 | 메트릭·로그·트레이스의 상관 분석 |
| 적합 구조 | 단일 서버·모놀리식 | 마이크로서비스·분산 시스템 |
| 결과 | 경보 | 원인 탐색·가설 검증 |
| 관계 | 옵저버빌리티의 일부 | 모니터링을 포함하는 상위 역량 |

### 텔레메트리 3요소

| 요소 | 내용 | 강점 | 약점 | 예 |
|---|---|---|---|---|
| 메트릭 | 시간에 따른 수치 집계 | 저장 비용 낮음, 추세·경보에 적합 | 세부 맥락 없음 | 초당 요청 수, 오류율, CPU |
| 로그 | 이벤트 단위 텍스트 기록 | 상세한 맥락 | 양이 많고 검색 비용 큼 | 오류 메시지, 감사 기록 |
| 트레이스 | 한 요청이 여러 서비스를 거친 경로와 구간별 시간 | 분산 구간 병목 파악 | 계측 필요, 표본 추출 | 결제 요청의 서비스별 지연 |

최근에는 여기에 코드 수준 자원 사용을 보여주는 **프로파일**과 배포·설정 변경 같은 **이벤트**를 더해 함께 분석한다. 세 요소를 **같은 요청 식별자**(트레이스 ID)로 묶어야 메트릭 이상 → 해당 요청의 트레이스 → 그 구간의 로그로 이어지는 탐색이 가능하다.

### 구성도 ① — 옵저버빌리티 파이프라인

```
 [서비스·인프라]  앱 · 컨테이너 · DB · 메시지 큐 · 클라우드 자원
      │  OpenTelemetry SDK·에이전트로 계측(트레이스 ID 전파)
      ▼
 [수집기]  수집 · 필터링 · 표본 추출 · 민감정보 마스킹
      │
      ▼
 [저장소]  메트릭 DB(시계열) · 로그 저장소 · 트레이스 저장소
      │
      ▼
 [분석]
   ├ 대시보드·SLO 현황
   ├ 경보(오류 예산 소진 속도 기반)
   └ AI 분석: 이상 탐지 · 경보 묶음 · 원인 후보 추천 · 요약
      │
      ▼
 [대응]  온콜 알림 → 런북 실행 → 복구 → 사후 분석
```

**OpenTelemetry**는 계측 방식을 표준화한 오픈소스 프로젝트로, 한 번 계측하면 수집·저장 도구를 바꿔도 코드를 다시 고칠 필요가 없게 해 준다. 특정 관측 제품에 종속되는 문제를 줄이는 것이 도입의 주된 이유다.

### 무엇을 볼 것인가 — 측정 방법

| 방법 | 지표 | 적용 대상 |
|---|---|---|
| 골든 시그널 | 지연 시간 · 트래픽 · 오류 · 포화도 | 사용자 대면 서비스 전반 |
| RED | 요청 비율(Rate) · 오류(Errors) · 처리 시간(Duration) | 마이크로서비스·API |
| USE | 사용률(Utilization) · 포화도(Saturation) · 오류(Errors) | CPU·메모리·디스크 등 자원 |

### SLO와 오류 예산 기반 경보
- **SLI**: 서비스 수준 지표(예: 300ms 이내 성공 응답 비율)
- **SLO**: SLI의 목표값(예: 30일 기준 99.9%)
- **오류 예산**: 100% − SLO. 99.9%라면 30일 동안 약 43분의 실패를 허용한다.
- **소진 속도 경보**: CPU 80% 같은 원인 지표가 아니라 **오류 예산이 얼마나 빨리 줄고 있는가**로 경보를 울린다. 사용자에게 실제로 영향이 있을 때만 사람을 깨우므로 경보 피로가 줄어든다.

### 구성도 ② — 장애 대응 생명주기와 AI 적용

```
 [탐지]     SLO 소진 경보 · 이상 탐지      ← AI: 계절성 반영 이상 탐지
    │       MTTD(평균 탐지 시간)
    ▼
 [분류]     영향 범위·심각도 판정          ← AI: 관련 경보 묶음(노이즈 제거)
    │       MTTA(평균 인지 시간)
    ▼
 [진단]     원인 후보 좁히기               ← AI: 토폴로지·트레이스 기반 원인 추천,
    │                                           직전 배포·설정 변경 연관 분석
    ▼
 [완화]     롤백 · 트래픽 우회 · 확장       ← AI: 런북 추천, 유사 과거 사고 검색
    │       MTTR(평균 복구 시간)
    ▼
 [사후 분석]  비난 없는 회고(Blameless Postmortem) ← AI: 타임라인·요약 초안 작성
            재발 방지 조치 → 계측·경보·런북 개선
```

장애 해결 시간 대부분은 **진단** 단계에서 쓰인다. AI가 수천 개 경보와 트레이스에서 원인 후보를 몇 개로 좁혀 주면 사람은 검증과 조치에 집중할 수 있다. 다만 AI의 원인 추천은 **상관관계에 근거한 후보**이므로, 조치 전에 사람이 확인하는 절차를 둔다.

### 도입 시 고려사항
- **비용**: 텔레메트리 양은 서비스 규모보다 빠르게 늘어난다. 표본 추출·보관 기간·로그 수준 관리가 필요하다.
- **민감정보**: 로그·트레이스에 개인정보·토큰이 섞이지 않도록 수집 단계에서 마스킹한다.
- **계측 표준**: 팀마다 계측 방식이 다르면 서비스 간 추적이 끊긴다. 트레이스 전파 표준(W3C Trace Context)과 공통 라이브러리를 정한다.
- **문화**: 사후 분석에서 개인을 비난하면 정보가 숨겨진다. 시스템 개선에 초점을 둔다.

### 관련 기준
- **OpenTelemetry**: 텔레메트리 계측·전송 표준(CNCF 프로젝트)
- **W3C Trace Context**: 분산 추적 식별자 전파 표준
- **Google SRE 원칙**: SLO·오류 예산·비난 없는 사후 분석
- **ITIL 4**: 모니터링·이벤트 관리, 인시던트 관리 관행

## 4. 연결 기출 토픽과 예상 변형

- **DevOps**: 블로그 통합 기출 분석(`exam_trend_integrated.json`) 기준 **DevOps는 기출 8회, 최근 출제 빈도**(recent 7)가 높은 키워드다. 옵저버빌리티는 DevOps의 운영 피드백 고리에 해당한다.
- **공공 SLA**: 139회 2교시에 **공공 SLA·정보시스템 등급제**가 출제됐다. SLA–SLO–SLI의 계층을 함께 정리하면 서비스 수준 문항에 바로 쓸 수 있다.
- **클라우드 네이티브**: 140회 3교시 **클라우드 네이티브 DR**, 140회 2교시 **서버리스**가 출제됐다. 분산된 클라우드 네이티브 구조일수록 옵저버빌리티가 필수다.
- **시계열 이상치**: 140회 4교시 **시계열 이상치 탐지**가 출제됐다. AI 이상 탐지의 기반 기법이다.
- **예상 변형**
  - 1교시: "옵저버빌리티(Observability)와 모니터링을 비교하시오"
  - 1교시: "SLO와 오류 예산(Error Budget)을 설명하시오"
  - 논술: "마이크로서비스 환경의 장애 대응 시간 단축을 위한 옵저버빌리티 체계 구축 방안을 제시하시오"

## 5. 답안 구성 예시

**단답형**(1교시, 1페이지)
- 정의: 메트릭·로그·트레이스 등 외부 텔레메트리로 시스템 내부 상태를 추론하고 미지의 문제 원인까지 찾는 능력
- 특징 3개: ① 텔레메트리 3요소의 트레이스 ID 기반 상관 분석 ② OpenTelemetry 표준 계측 ③ SLO·오류 예산 기반 경보
- 구성도 키워드: 계측(OpenTelemetry) → 수집기 → 메트릭·로그·트레이스 저장소 → 분석(대시보드·경보·AI) → 대응

**논술형(2~4교시) 목차**
1. 개요: 분산 서비스 확산과 장애 진단 시간 문제
2. 구성/비교: 모니터링 vs 옵저버빌리티 비교표, 텔레메트리 3요소 표, 파이프라인 구성도, 장애 대응 생명주기도
3. 적용방안: OpenTelemetry 표준 계측, SLO 정의와 소진 속도 경보, AI 경보 묶음·원인 추천, 런북 자동화, 비난 없는 사후 분석
4. 고려사항: 텔레메트리 비용, 민감정보 마스킹, 계측 표준 불일치, AI 추천의 상관관계 한계
5. 기술사 제언: 옵저버빌리티 성과를 도구 도입이 아니라 **MTTD·MTTR 단축과 SLO 달성률**로 측정하고, AI 원인 추천은 사람의 검증을 거치는 보조 수단으로 운영할 것
