## 1. 뉴스 요약

전자신문(11-04)은 **티벨이 전문 QA 인력과 관리 플랫폼을 결합한 구독형 품질검증 서비스 'T-ASSI'를 운영**한다고 보도했다. 개발 조직이 테스트 전문 인력을 상시 고용하지 않고도, 필요한 기간·범위만큼 **외부의 독립된 품질검증 역량을 구독 방식으로 쓰는** 모델이다. 개발 속도가 빨라지고 AI가 코드를 대량으로 생성하면서, "누가 객관적으로 검증하는가"가 다시 중요한 질문이 되고 있다. 서비스의 세부 구성은 제목 이상으로 확인되지 않으므로, 아래에서는 **품질검증의 서비스화와 독립 검증**(IV&V) 개념을 답안 재료로 정리한다.

## 2. 핵심 개념

### 정의
**IV&V**(Independent Verification and Validation, 독립 검증·확인)는 개발 조직과 **기술·관리·재정적으로 독립된 주체**가 소프트웨어가 명세대로 만들어졌는지(검증, Verification), 사용자의 실제 요구를 충족하는지(확인, Validation)를 평가하는 활동이다. **구독형 QA 서비스**는 이런 외부 검증 역량을 인력과 도구(테스트 관리 플랫폼)를 묶어 기간제로 제공하는 방식으로, 독립성과 전문성을 비교적 낮은 고정비로 확보하려는 시도다.

### 검증(Verification) vs 확인(Validation)

| 구분 | 검증(Verification) | 확인(Validation) |
|---|---|---|
| 질문 | 제품을 올바르게 만들었는가 | 올바른 제품을 만들었는가 |
| 기준 | 설계·명세서 | 사용자 요구·운영 환경 |
| 주요 시점 | 각 개발 단계 산출물 | 통합·인수 단계 |
| 활동 | 리뷰·인스펙션·단위·통합 테스트 | 시스템·인수 테스트, 사용자 평가 |
| 실패 예 | 명세와 다르게 구현 | 명세대로 만들었지만 쓸모가 없음 |

### 구성도 — 개발 조직과 독립 검증의 관계

```
 ┌──────────── 발주·경영 ─────────────┐
 │  요구 정의 · 예산 · 최종 승인       │
 └──────┬───────────────────┬────────┘
        │ 개발 지시          │ 검증 의뢰(보고 라인 분리)
        ▼                   ▼
 ┌─────────────┐     ┌──────────────────────────┐
 │  개발 조직   │     │  독립 검증 조직(IV&V/QA)   │
 │ 설계·구현·단위│◀───▶│ 요구 추적 · 리뷰 · 테스트 │
 │ 테스트       │결함  │ 설계·실행 · 결함 관리      │
 └─────────────┘보고  │ (전문 인력 + 관리 플랫폼)  │
                      └────────────┬─────────────┘
                                   ▼
                      품질 보고서 · 출시 판정 근거 → 발주·경영
```

독립성을 가르는 기준은 **보고 라인**이다. 검증 조직이 개발 책임자에게만 보고하면 일정 압박 앞에서 결함이 축소 보고되기 쉽다. 독립 검증은 결과를 **발주자·경영진에게 직접** 전달하는 구조로 객관성을 지킨다.

### IV&V의 독립성 유형(IEEE 1012)

| 유형 | 내용 | 훼손 사례 |
|---|---|---|
| 기술적 독립성 | 개발과 다른 인력·도구·방법으로 검증 | 개발자가 만든 테스트를 그대로 재실행 |
| 관리적 독립성 | 개발 조직과 분리된 보고 라인 | 개발 PM이 검증 결과 공개 여부 결정 |
| 재정적 독립성 | 개발 예산과 분리된 검증 예산 | 결함이 많으면 검증 비용을 깎는 구조 |

### 내부 QA · 외부 QA 서비스 · 감리 · PMO 비교

| 구분 | 내부 QA 조직 | 외부 QA·IV&V 서비스 | 정보시스템 감리 | PMO |
|---|---|---|---|---|
| 주 목적 | 상시 품질 활동 | 독립적 품질 검증 | 사업 적정성 점검 | 사업 관리 지원 |
| 관점 | 제품 품질 | 제품 품질 | 사업·산출물 적합성 | 일정·범위·위험 |
| 독립성 | 낮음~중간 | 높음 | 높음(제3자) | 발주자 측 |
| 수행 시점 | 상시 | 계약 기간 | 단계별 점검 | 사업 전 기간 |
| 비용 구조 | 고정 인건비 | 기간·범위별 변동비 | 사업비 일부 | 사업비 일부 |
| 강점 | 도메인 이해 | 전문성·객관성 | 법적 근거(공공) | 통합 관리 |

### 테스트 프로세스 성숙도 — TMMi
외부 QA를 쓰더라도 조직 스스로의 테스트 역량이 낮으면 효과가 오래가지 않는다. **TMMi**(Test Maturity Model integration)는 테스트 프로세스 성숙도를 5단계로 구분한다.
1. **초기**(Initial): 체계 없는 임의 테스트
2. **관리**(Managed): 테스트 정책·계획·설계·실행·환경 관리
3. **정의**(Defined): 조직 표준 프로세스, 비기능 테스트, 동료 검토
4. **측정**(Measured): 테스트 측정, 제품 품질 평가
5. **최적화**(Optimization): 결함 예방, 품질 통제, 지속 개선

### 관련 표준
- **IEEE 1012**: 시스템·소프트웨어·하드웨어 검증·확인(V&V) 표준 — 무결성 수준에 따라 V&V 강도를 차등
- **ISO/IEC/IEEE 29119**: 소프트웨어 테스팅 프로세스·문서·기법
- **ISO/IEC 25010**: 소프트웨어 제품 품질 모델(평가 기준)
- **GS 인증**(TTA): 소프트웨어 품질 인증 — 외부 평가의 국내 사례

- IV&V의 정의와 필요성
- 검증(Verification)과 확인(Validation)의 차이
- 독립성 3유형(기술적·관리적·재정적)
- 보고 라인 분리를 통한 객관성 확보
- 내부 QA·외부 QA 서비스·감리·PMO 비교
- 구독형 QA 서비스의 장단점(전문성·비용 vs 도메인 이해)
- TMMi 5단계 테스트 성숙도
- IEEE 1012 무결성 수준별 V&V 강도 차등
- AI 생성 코드 증가와 독립 검증의 중요성

## 4. 연결 기출 토픽과 예상 변형

- **테스트 기본기**: 139회 3교시 **SW 테스트 7원리·동등분할·경계값 분석**, 140회 3교시 **메타모픽 테스트**가 출제됐다. 테스트 기법 다음 단계로 **"누가 어떤 체계로 테스트하는가"**(조직·프로세스)를 묻는 변형이 자연스럽다.
- **품질 모델**: 140회 1교시 **ISO/IEC 25010 주특성·부특성**이 출제됐다. 외부 검증은 25010 기준의 품질 평가를 객관적으로 수행하는 주체다.
- **PMO·형상관리**: 140회 1교시 **PMC vs PMO**, 4교시 **소프트웨어 형상관리**(SCM)가 출제됐다. IV&V와 PMO·감리를 비교하는 표는 이 문항들과 묶어 쓸 수 있다.
- **예상 변형**
  - 1교시: "IV&V(Independent Verification and Validation)의 개념과 독립성 유형을 설명하시오"
  - 1교시: "TMMi(Test Maturity Model integration)의 단계를 설명하시오"
  - 논술: "AI 기반 개발 환경에서 소프트웨어 품질 확보를 위한 독립 검증 체계를 제시하시오"

## 5. 답안 구성 예시

**단답형**(1교시, 1페이지)
- 정의: 개발과 독립된 주체가 명세 적합성(검증)과 요구 충족(확인)을 평가하는 활동
- 특징 3개: ① 기술적·관리적·재정적 독립성 ② 발주자 직접 보고 ③ 무결성 수준별 강도 차등(IEEE 1012)
- 구성도 키워드: 발주·경영 → 개발 조직 / 독립 검증 조직(요구 추적·리뷰·테스트) → 품질 보고 → 출시 판정

**논술형(2~4교시) 목차**
1. 개요: 개발 속도 증가·AI 생성 코드 확산과 객관적 검증 수요
2. 구성/비교: 독립 검증 구성도, 검증 vs 확인 비교표, 내부 QA·외부 QA·감리·PMO 비교표
3. 적용방안: 위험도 기반 IV&V 범위 설정, 구독형 QA로 피크 대응, 테스트 관리 플랫폼 공유, TMMi 기반 내부 역량 강화
4. 고려사항: 외부 인력의 도메인 이해 부족, 보안(코드·데이터 접근), 독립성 훼손 요인, 비용 대비 효과 측정
5. 기술사 제언: 외부 QA를 단순 인력 보충이 아닌 **독립 검증 기능**으로 계약하고, 결과 보고 라인을 개발 조직과 분리하며, 동시에 내부 테스트 성숙도를 단계적으로 끌어올릴 것
