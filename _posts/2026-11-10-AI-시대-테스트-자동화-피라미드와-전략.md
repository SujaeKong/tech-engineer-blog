## 1. 뉴스 요약

전자신문(11-06)은 **와이즈스톤이 "반복 업무는 AI에게, 엔지니어는 품질에 집중"을 내걸고 테스트 자동화 플랫폼 'TestClaw'를 공개**했다고 보도했다. 같은 날 전자신문은 **플래티어가 국제 품질 테스팅 콘퍼런스(BeSTCon 2026)에서 AI 테스트 관리 솔루션 'XGEN TMS'를 처음 선보였다**고 전했고, 앞서(11-05) **슬렉슨이 같은 행사에서 AI 개발 시대의 품질·검증 전략**을 제시했다고 보도했다. AI가 코드를 빠르게 만들수록 **사람이 손으로 하는 테스트로는 따라가기 어렵다**는 문제의식이 공통이다. 각 제품의 기능은 제목 이상으로 확인되지 않으므로, 아래에서는 **테스트 자동화의 구조와 전략**을 정리한다.

## 2. 핵심 개념

### 정의
**테스트 자동화**는 테스트 케이스의 실행·결과 비교·보고를 도구로 반복 수행해 **회귀 결함을 빠르게 찾고 출시 주기를 짧게** 만드는 활동이다. **테스트 자동화 피라미드**는 자동화 테스트를 **아래(단위)는 많이, 위(UI·E2E)는 적게** 구성해야 비용 대비 효과가 크다는 설계 원칙으로, 마이크 콘(Mike Cohn)이 제시했다.

### 구성도 — 테스트 자동화 피라미드와 안티패턴

```
       바람직한 피라미드                     아이스크림 콘(안티패턴)

            /\    UI·E2E (소수)              ████████████  수동 테스트
           /  \   느림·깨지기 쉬움            ██████████    UI·E2E 다수
          /────\                              ███████
         / 서비스\  API·통합 (중간)              ████        통합 소수
        /  통합   \                               ██          단위 거의 없음
       /──────────\                               ▼
      /    단위     \ 단위 (다수)
     /  빠름·저비용  \ 빠름·안정적
    /────────────────\
```

피라미드가 뒤집히면 테스트 실행이 느리고 자주 깨져서, 자동화를 해 놓고도 **결과를 믿지 못하는** 상황이 된다.

### 피라미드 계층 비교

| 계층 | 대상 | 실행 속도 | 유지보수 비용 | 결함 위치 파악 | 권장 비중 |
|---|---|---|---|---|---|
| 단위 | 함수·클래스 | 매우 빠름(ms) | 낮음 | 정확 | 가장 많이 |
| 서비스·통합 | API·모듈 연동 | 빠름(초) | 중간 | 비교적 정확 | 중간 |
| UI·E2E | 사용자 시나리오 전체 | 느림(분) | 높음(화면 변경에 취약) | 어려움 | 핵심 경로만 |
| 수동·탐색적 | 사용성·예외 상황 | 매우 느림 | — | 사람 판단 | 자동화가 어려운 영역 |

### 자동화 대상 선정 기준

| 자동화에 적합 | 자동화에 부적합 |
|---|---|
| 자주 반복 실행되는 회귀 테스트 | 한 번만 하는 테스트 |
| 결과 판정이 명확한 테스트 | 사용성·디자인처럼 주관적 판단 |
| 데이터 조합이 많은 테스트 | 요구사항이 자주 바뀌는 초기 기능 |
| 사람이 하면 실수가 잦은 반복 작업 | 탐색적 테스트 |
| 출시마다 반드시 확인할 핵심 기능 | 자동화 비용이 효과보다 큰 영역 |

### 자동화 ROI와 불안정 테스트
- **ROI**: (수동 실행 비용 × 반복 횟수 − 자동화 구축·유지 비용) ÷ 자동화 구축·유지 비용. **실행 횟수가 많을수록** 이익이 커지므로 회귀 테스트부터 자동화한다.
- **불안정 테스트**(Flaky Test): 코드 변경이 없는데도 통과·실패가 번갈아 나오는 테스트. 시간 의존, 테스트 간 순서 의존, 비동기 대기, 외부 서비스 의존이 원인이다. 불안정 테스트가 쌓이면 실패 결과를 무시하는 습관이 생겨 자동화 전체의 신뢰가 무너진다. **격리·재현 분석·수정 또는 제거**를 운영 절차로 둔다.

### AI가 바꾸는 자동화 영역

| 영역 | 기존 | AI 적용 |
|---|---|---|
| 테스트 케이스 작성 | 사람이 명세를 읽고 작성 | 요구사항·코드에서 후보 자동 생성 |
| UI 테스트 유지 | 화면 요소 변경 시 스크립트 수정 | 요소 위치가 바뀌어도 자동으로 찾는 자가 치유(self-healing) |
| 결과 분석 | 실패 로그를 사람이 분류 | 실패 원인 군집화·중복 결함 묶기 |
| 테스트 선택 | 전체 회귀 실행 | 변경 영향 기반 우선순위 선택 |
| 테스트 데이터 | 수작업 준비 | 합성 테스트 데이터 생성 |

AI가 테스트를 대신 만들어도 **무엇을 검증해야 하는지(오라클)는 사람이 정해야** 한다. 생성된 테스트가 버그가 있는 현재 동작을 정답으로 고정해 버리는 위험도 있다.

### 관련 표준
- **ISO/IEC/IEEE 29119**: 소프트웨어 테스팅 표준 — 29119-5는 키워드 주도 테스팅(자동화 스크립트를 업무 언어 키워드로 구성)을 다룸
- **ISO/IEC 25010**: 품질 특성 — 자동화 대상 선정 시 기능 적합성·신뢰성 우선 검증
- **TMMi**: 테스트 프로세스 성숙도 — 자동화는 성숙한 테스트 프로세스 위에서 효과가 난다

## 4. 연결 기출 토픽과 예상 변형

- **테스트 기본기**: 139회 3교시 **SW 테스트 7원리·동등분할·경계값 분석**이 출제됐다. 7원리 중 "살충제 패러독스"는 같은 자동화 테스트만 반복하면 새 결함을 못 찾는다는 점에서 자동화 전략과 바로 연결된다.
- **메타모픽 테스트**: 140회 3교시 **메타모픽 테스트**가 출제됐다. 정답(오라클)이 불명확한 AI 출력의 자동화 검증 기법으로 함께 쓸 수 있다.
- **배포·형상관리**: 139회 1교시 **SW 무중단 배포**, 140회 4교시 **소프트웨어 형상관리**(SCM)가 출제됐다. CI/CD 파이프라인 안의 자동화 테스트는 두 주제를 잇는 고리다.
- **예상 변형**
  - 1교시: "테스트 자동화 피라미드를 설명하시오"
  - 1교시: "불안정 테스트(Flaky Test)의 원인과 대응 방안을 설명하시오"
  - 논술: "AI 기반 개발 환경에서 테스트 자동화 전략과 품질 보증 체계를 제시하시오"

## 5. 답안 구성 예시

**단답형**(1교시, 1페이지)
- 정의: 단위 테스트를 가장 많이, UI·E2E 테스트를 가장 적게 구성하는 자동화 테스트 설계 원칙(Mike Cohn)
- 특징 3개: ① 하위 계층일수록 빠르고 안정적 ② 아이스크림 콘 안티패턴 회피 ③ CI 연동으로 매 변경마다 실행
- 구성도 키워드: 단위(다수) → 서비스·통합(중간) → UI·E2E(소수) + 수동·탐색적 테스트

**논술형(2~4교시) 목차**
1. 개요: AI 코드 생성 확산과 수동 테스트의 한계
2. 구성/비교: 피라미드·안티패턴 구성도, 계층 비교표, 자동화 대상 선정표, AI 적용 영역표
3. 적용방안: 단위 테스트 우선 확충, 핵심 경로 E2E 한정, 변경 영향 기반 테스트 선택, 불안정 테스트 격리 절차, AI 테스트 생성 검토 단계
4. 고려사항: 자동화 유지보수 비용, 오라클 문제, AI 생성 테스트의 잘못된 정답 고정, 탐색적 테스트의 필요성
5. 기술사 제언: 자동화 성과를 **테스트 개수가 아닌 결함 검출 시점·회귀 결함 유출률**로 측정하고, AI가 만든 테스트도 사람이 검증 기준을 확인한 뒤 채택할 것
