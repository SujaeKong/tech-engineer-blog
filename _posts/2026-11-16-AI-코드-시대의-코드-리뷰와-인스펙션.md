## 1. 뉴스 요약

뉴시스(11-13)는 테스트뮤 AI의 '2026 품질 엔지니어링 분야 AI 현황 보고서'를 인용해 **소프트웨어 팀의 81%가 AI가 작성한 코드를 제대로 이해하지 못한 채 병합한 경험이 있다**고 보도했다. 같은 날 피앤피뉴스(11-13)는 **테스티파이가 생성형 AI로 소프트웨어 품질검증을 바꾸는 기술**로 G-스타 오디션 대상을 받았다고 전했다. 코드를 만드는 속도는 AI로 크게 빨라졌지만, 그 코드를 **사람이 읽고 이해하고 책임지는 단계**가 따라가지 못하고 있다는 신호다. 보고서의 조사 방법과 세부 수치는 제목 이상으로 확인되지 않으므로, 아래에서는 **소프트웨어 리뷰 기법과 AI 생성 코드 리뷰 체계**를 정리한다.

## 2. 핵심 개념

### 정의
**소프트웨어 리뷰**는 코드·설계서 같은 산출물을 **실행하지 않고 사람이 검토해 결함과 개선점을 찾는 정적 검증 활동**이다(IEEE 1028). 그중 **인스펙션**(Inspection)은 역할·절차·체크리스트·결함 측정이 정해진 **가장 정형적인 리뷰**로, 테스트보다 이른 시점에 싸게 결함을 걷어내는 것이 목적이다. AI 생성 코드가 늘면서 리뷰는 결함 탐지뿐 아니라 **"팀이 이 코드를 이해하고 있는가"를 확인하는 관문** 역할이 커졌다.

### IEEE 1028 리뷰 유형 비교

| 유형 | 목적 | 주도자 | 정형성 | 주요 산출물 |
|---|---|---|---|---|
| 관리 검토 | 진척·계획·위험 점검, 관리 의사결정 | 관리자 | 중간 | 조치 항목, 의사결정 기록 |
| 기술 검토 | 기술적 적합성·대안 평가 | 기술 리더 | 중간 | 기술 이슈 목록, 권고안 |
| 인스펙션 | 결함 탐지·제거, 프로세스 개선 데이터 | 훈련된 중재자 | 높음 | 결함 목록, 결함 통계 |
| 워크스루 | 작성자 설명으로 이해 공유·대안 모색 | 작성자 | 낮음~중간 | 의견·개선 아이디어 |
| 감사 | 표준·규정·계약 준수 여부 독립 확인 | 외부·독립 감사인 | 높음 | 감사 보고서, 부적합 사항 |
| 동료 검토(비공식) | 빠른 피드백(PR 리뷰·데스크 체크) | 동료 개발자 | 낮음 | 코멘트 |
| 페어 프로그래밍 | 작성과 동시에 실시간 검토 | 두 개발자 | 낮음 | 코드 자체 |

### 구성도 ① — 페이건 인스펙션 절차와 역할

```
 역할: 중재자(Moderator) · 작성자(Author) · 낭독자(Reader)
       · 기록자(Recorder) · 검토자(Inspector)

 [1. 계획]   중재자가 대상·참가자·체크리스트·일정 확정, 진입 조건 확인
     ▼
 [2. 개요]   작성자가 대상의 목적·구조를 간단히 설명(선택)
     ▼
 [3. 준비]   검토자 각자 체크리스트로 개별 검토 ← 결함 대부분이 여기서 발견
     ▼
 [4. 회의]   낭독자가 코드를 읽어 가며 결함 확인, 기록자가 기록
             (해결책 토론은 하지 않고 결함 식별에 집중)
     ▼
 [5. 재작업] 작성자가 결함 수정
     ▼
 [6. 후속]   중재자가 수정 확인, 종료 조건 판단, 결함 데이터 축적
```

인스펙션이 워크스루와 갈리는 지점은 **작성자가 진행하지 않는다**는 점이다. 작성자가 설명하면 검토자가 작성자의 논리를 따라가게 되어 결함을 놓치기 쉽기 때문이다.

### 사람 작성 코드 리뷰 vs AI 생성 코드 리뷰

| 구분 | 사람 작성 코드 | AI 생성 코드 |
|---|---|---|
| 작성 의도 설명 | 작성자가 근거를 설명할 수 있음 | 제출자도 세부 근거를 모를 수 있음 |
| 변경 분량 | 상대적으로 작음 | 한 번에 큰 변경이 쉽게 생성됨 |
| 결함 양상 | 오타·논리 실수 등 국소적 | 그럴듯하지만 요구와 어긋난 구현, 존재하지 않는 API, 과도한 중복 |
| 보안 위험 | 개인 숙련도에 좌우 | 취약 패턴 재생산, 오래된 라이브러리 사용 |
| 라이선스 | 출처가 비교적 명확 | 학습 데이터 유래 코드 혼입 가능성 |
| 리뷰 초점 | 결함 탐지 | 결함 탐지 + 요구 적합성 + 팀의 이해 확보 |
| 책임 소재 | 작성자 | 병합을 승인한 제출자·리뷰어 |

### 이해 부채(Comprehension Debt)
팀이 **이해하지 못한 채 병합한 코드가 쌓이면서 생기는 미래 비용**을 이해 부채라고 부르는 시각이 있다. 장애가 나거나 기능을 바꿔야 할 때 누구도 코드를 설명하지 못해 분석 시간이 길어진다. 기술부채의 한 형태로 볼 수 있으며, 일반 기술부채가 "알고도 미룬 설계 결함"이라면 이해 부채는 "**모르는 채로 들어온 코드**"라는 점이 다르다. 유지보수성(ISO/IEC 25010의 분석성·수정성)을 직접 깎아 먹는다.

### 구성도 ② — AI 시대의 리뷰 게이트

```
 [AI 생성 코드 제출]  커밋·PR에 AI 사용 여부 표시
        │
        ▼
 [자동 게이트]  빌드 · 단위 테스트 · 정적 분석 · SAST · 의존성·라이선스 검사
        │  실패 시 사람 리뷰 전에 반려
        ▼
 [AI 리뷰 보조]  변경 요약 · 위험 지점 표시 · 누락 테스트 제안
        │
        ▼
 [사람 리뷰]  요구 적합성 · 설계 일관성 · 제출자의 설명 가능 여부 확인
        │     핵심 모듈은 2인 승인, 대규모 변경은 분할 요구
        ▼
 [병합]  ──▶ [운영 모니터링·결함 데이터] ──▶ 체크리스트·게이트 기준 개선
```

### 리뷰 효과를 높이는 실무 기준
- **변경 단위 제한**: 한 번에 검토하는 코드가 많을수록 결함 탐지율이 떨어진다. 한 번에 수백 줄 이내로 나누라는 지침이 흔히 인용된다.
- **설명 가능성 원칙**: 제출자가 동작과 근거를 설명하지 못하는 AI 생성 코드는 병합하지 않는다.
- **체크리스트 갱신**: AI 코드에서 반복되는 결함 유형(존재하지 않는 API, 예외 처리 누락, 하드코딩된 비밀값)을 체크리스트에 반영한다.
- **측정**: 리뷰 속도(시간당 검토 줄 수), 결함 발견 밀도, 리뷰 후 유출 결함 수로 리뷰 품질을 관리한다.

### 관련 표준
- **IEEE 1028**: 소프트웨어 리뷰와 감사 — 관리 검토·기술 검토·인스펙션·워크스루·감사 정의
- **ISO/IEC 20246**: 작업 산출물 리뷰(Work Product Reviews) 절차
- **ISO/IEC/IEEE 29119**: 소프트웨어 테스팅 — 리뷰를 정적 테스팅으로 포함
- **ISO/IEC 25010**: 품질 모델 — 유지보수성(분석성·수정성·시험성)

## 4. 연결 기출 토픽과 예상 변형

- **기술부채**: 139회 3교시에 **기술부채**가 출제됐다. 이해 부채를 기술부채의 새로운 유형으로 제시하고, 리뷰 게이트를 상환·예방 수단으로 쓰면 차별화된 답안이 된다.
- **테스트 원리**: 139회 3교시 **테스트 7원리·동등분할·경계값 분석**이 출제됐다. 리뷰는 동적 테스트 이전의 정적 테스팅으로, "결함은 일찍 찾을수록 싸다"는 조기 테스팅 원리와 연결된다.
- **품질 모델**: 140회 1교시 **ISO 25010**이 출제됐다. 이해 부채가 유지보수성 하위 특성을 떨어뜨린다는 논리로 묶을 수 있다.
- **SW 공급망**: 140회 2교시 **오픈소스 라이선스와 SW 공급망**이 출제됐다. AI 생성 코드의 라이선스 혼입 검사가 리뷰 게이트의 한 단계다.
- **예상 변형**
  - 1교시: "인스펙션(Inspection)과 워크스루(Walkthrough)를 비교하시오"
  - 1교시: "IEEE 1028의 소프트웨어 리뷰 유형을 설명하시오"
  - 논술: "생성형 AI 코딩 도구 확산에 따른 코드 리뷰 체계 개선 방안을 제시하시오"

## 5. 답안 구성 예시

**단답형**(1교시, 1페이지)
- 정의: 훈련된 중재자가 정해진 역할·절차·체크리스트로 산출물의 결함을 찾아 제거하는 가장 정형적인 리뷰(인스펙션)
- 특징 3개: ① 작성자가 아닌 중재자·낭독자 주도 ② 개별 준비 단계에서 결함 대부분 발견 ③ 결함 데이터를 축적해 프로세스 개선
- 구성도 키워드: 계획 → 개요 → 준비 → 회의 → 재작업 → 후속 / 중재자·작성자·낭독자·기록자·검토자

**논술형(2~4교시) 목차**
1. 개요: AI 생성 코드의 무이해 병합 실태와 리뷰의 역할 변화
2. 구성/비교: IEEE 1028 유형 비교표, 인스펙션 절차도, 사람 vs AI 코드 리뷰 비교표
3. 적용방안: AI 사용 표시, 자동 게이트 선행, AI 리뷰 보조, 설명 가능성 원칙, 핵심 모듈 2인 승인, 변경 분할
4. 고려사항: 리뷰어 피로·형식적 승인, 리뷰 병목에 따른 생산성 저하, AI 리뷰 도구의 오탐, 책임 소재
5. 기술사 제언: 리뷰 성과를 승인 속도가 아니라 **유출 결함 감소와 팀의 코드 설명 가능성**으로 측정하고, AI가 늘린 생산량만큼 리뷰·테스트 역량에 투자를 재배분할 것
